    Backup i rclone¶

    Komendy¶

    make db-backup        # Pojedynczy pg_dump (równoległy, tar.gz)
make config-backup    # Archiwum katalogu konfiguracyjnego (.env, rclone.conf, ssl/ ...)
make restore-config FILE=...   # Odtworzenie konfiguracji z archiwum
make backup-cycle     # Pełen cykl: pg_dump + tar mediów i konfiguracji + rclone copy + retencja zdalna
make rclone-config    # Konfiguracja zdalnego backupu (Google Drive, S3, ...)
make rclone-sync      # Wymuszona wysyłka do chmury (ten sam układ co cykl nocny)
make rclone-check     # Sprawdzenie spójności kopii zdalnej
make images-save      # Archiwum obrazów Dockera + git bundle repo (praca bez Docker Huba/GitHuba)
make images-load FILE=...      # Wczytanie archiwum obrazów i weryfikacja z manifestem

    Codzienny backup¶

    Codzienny backup uruchamia Ofelia o 01:45 czasu polskiego (label 0 45 1 * * * na backup-runner; strefa harmonogramów Ofelii — BPP_CRON_TZ). backup-runner to orkiestrator (obraz docker:28-cli): sam nie ma ani pg_dump, ani rclone'a — wykonuje sekwencję cyklu, a ciężkie kroki deleguje przez docker exec do kontenerów, które i tak istnieją i mają właściwe narzędzia:

    1. pg_dump — w kontenerze dbserver, więc wersja klienta zawsze równa się wersji serwera (w trybie external — sentinela postgres:<major>-alpine),
    2. tar dumpu, mediów i katalogu konfiguracyjnego — lokalnie (busybox tar; /backup, wolumen media i $BPP_CONFIGS_DIR są zamontowane także w orkiestratorze),
    3. rotacja lokalna (DJANGO_BPP_BACKUP_KEEP_LAST) — tylko po udanym zrzucie bazy i mediów, więc nieudany backup nie kasuje starych kopii,
    4. archiwum obrazów Dockera i repozytorium — tylko przy wolnym miejscu na dysku i gdy zmieniły się obrazy działających kontenerów (docker save przez socket); idzie po rotacji, żeby rezerwa dysku liczyła wolne miejsce bez nadmiarowego kompletu kopii,
    5. rclone copy + retencja zdalna — w serwisie rclone (patrz niżej),
    6. notyfikacja do Rollbara i/lub GlitchTipa — docker exec appserver python (bez curl/jq); każdy kanał tylko, gdy skonfigurowany.
    7. heartbeat do Healthchecks.io — busyboxowy wget z samego orkiestratora (opcjonalnie, DJANGO_BPP_HEALTHCHECKS_PING_KEY).

    Kontenery są adresowane po labelach compose (com.docker.compose.service), nigdy po nazwie — nazwy generuje compose.

    Dwa obrazy, zero doinstalowywania w runtime

    Do września 2026 backup-runner startował na obrazie postgres (współdzielonym z dbserverem) i doinstalowywał rclone, curl, jq i ca-certificates przez apt-get przy każdym starcie — każdy start wymagał sieci i repozytorium Debiana, a awaria tej instalacji była cicha aż do nocnego cyklu (tak weszła awaria TLS). Teraz obrazy są dwa i oba gotowe od razu:

    • backup-runner — docker:28-cli (override: BPP_ORCHESTRATOR_IMAGE w .env),
    • rclone — rclone/rclone:1.71.0 (override: BPP_RCLONE_IMAGE w .env).

    Zmienna BPP_BACKUP_PG_IMAGE (dawny override obrazu backup-runnera w trybie external) jest martwa: nic jej nie czyta, w starym .env jest tolerowana i ignorowana — nie trzeba jej usuwać.

    Wdrożenie orkiestratora wymaga make up

    Migracja na orkiestrator to jedna jednostka wdrożeniowa: zmiana obrazów i command: w docker-compose.backup.yml razem z nowymi skryptami. Sam git pull jej nie wdraża (inaczej niż zwykłe zmiany w scripts/, które jadą na bind-mouncie i wchodzą przy najbliższym cyklu) — stary kontener nie ma docker ani socketu, więc nowy backup-cycle.sh wołany w nim przez Ofelię padnie, a notyfikacja o tym nie wyjdzie. Zrób git pull && make up jednym ciągiem.

    make backup-cycle uruchamia ten sam cykl ręcznie.

    Wyłączenie nocnego backupu — DJANGO_BPP_BACKUP_ENABLED¶

    Na instalacji, na której backup nie jest potrzebny (np. testowej, bez skonfigurowanego rclone'a), nocny cykl kończyłby się co noc błędem rclone-config-missing i zgłoszeniem do Rollbara/GlitchTipa. Żeby go wyłączyć, wpisz w $BPP_CONFIGS_DIR/.env (albo make configure → Backup):

    DJANGO_BPP_BACKUP_ENABLED=0

    To flaga 1/0, jak inne flagi BPP (np. ZGLOS_CAPTCHA_ENABLED). Świeża instalacja dostaje DJANGO_BPP_BACKUP_ENABLED=1. Dla wygody działają też false/true i nie/tak (oraz no/yes, off/on; wielkość liter bez znaczenia) — wpisane już wcześniej tak/nie nie wymagają zmiany.

    Wartość Nocny cykl
    brak zmiennej, pusta, 1 (także true, tak, yes, on) włączony — jak dotąd
    0 (także false, nie, no, off) pomijany
    cokolwiek innego (literówka) włączony + ostrzeżenie w logu cyklu

    Wyłączony cykl o 01:45 zapisuje w logu jedną linię (backup wylaczony przez DJANGO_BPP_BACKUP_ENABLED=0 - pomijam cykl) i kończy się sukcesem przed jakimkolwiek krokiem: nie robi zrzutu bazy ani archiwów, niczego nie wysyła rclone'em, nie rusza retencji (lokalnej ani zdalnej) i nie wysyła żadnej notyfikacji — ani do Rollbara/GlitchTipa, ani pingu do Healthchecks.io.

    Ręczne backupy działają zawsze, niezależnie od zmiennej — operator świadomie o nie prosi: make backup, make db-backup, make media-backup, make config-backup, make rclone-sync, a także make backup-cycle (i punkt 5 w make doctor), który omija wyłącznik i odnotowuje to w logu.

    Healthchecks.io: wstrzymaj albo usuń kontrolę <hostname>-backup

    Wyłączony cykl nie wysyła żadnego pingu, więc jeśli instalacja ma heartbeat, Healthchecks po upływie grace zaalarmuje o brakującym backupie. Przy wyłączaniu backupu wstrzymaj (Pause) albo usuń tę kontrolę w panelu. Po ponownym włączeniu kontrola wznowi się sama przy pierwszym pingu.

    Czy potrzebny make up? Zwykle nie: cykl czyta zmienną z pliku $BPP_CONFIGS_DIR/.env zamontowanego w backup-runnerze (/configs), więc zmiana działa od najbliższego cyklu — także ponowne włączenie. Środowisko kontenera (env_file) jest tylko migawką z ostatniego make up i służy wyłącznie jako zapas, gdy kontener nie ma mountu /configs (utworzony przed wprowadzeniem backupu konfiguracji) — wtedy zrób git pull && make up jeden raz.

    Monitoring backupu — Healthchecks.io¶

    Rollbar dostaje komunikat tylko z cyklu, który się wykonał — i tylko wtedy, gdy działa appserver. Nie wykryje sytuacji, w której backup w ogóle nie ruszył: padnięta Ofelia, niedziałający backup-runner, wyłączony serwer, cykl zawieszony w połowie. Do tego służy opcjonalny heartbeat do Healthchecks.io („dead man's switch"): serwis alarmuje, gdy w zadanym czasie nie przyszedł ping o udanym backupie.

    Cykl wysyła trzy rodzaje pingów:

    Kiedy Adres Treść
    start cyklu …/<slug>/start — (Healthchecks mierzy czas trwania)
    sukces …/<slug> podsumowanie: rozmiary, katalog zdalny, czas, retencja
    błąd kroku …/<slug>/fail nazwa kroku, kod wyjścia, końcówka logu

    Ping idzie z orkiestratora (wget z obrazu docker:28-cli), nie przez appservera — ma dojść także wtedy, gdy aplikacja leży. Nieudany ping (brak sieci, timeout; 3 próby) zostawia ostrzeżenie w logu i nigdy nie zmienia wyniku ani kodu wyjścia backupu.

    Włączenie¶

    1. Załóż projekt w Healthchecks.io i skopiuj Ping key (Settings → Ping key).

    2. Wpisz go do $BPP_CONFIGS_DIR/.env (albo make configure → Powiadomienia):

      DJANGO_BPP_HEALTHCHECKS_PING_KEY=<ping-key>

    3. Odtwórz orkiestrator, żeby zobaczył nowy klucz:

      docker compose up -d --no-deps backup-runner

      env_file jest wczytywany przy tworzeniu kontenera, nie przy każdym cyklu — sam git pull (ani sama edycja .env) nie wystarczy; make up też załatwia sprawę. Restartuje się tylko bezczynny orkiestrator, aplikacja działa dalej.

      Kontrola zakłada się sama przy pierwszym pingu (?create=1) pod slugiem <DJANGO_BPP_HOSTNAME>-backup, małymi literami, z kropkami zamienionymi na - (np. bpp-example-org-backup). Instalacje multi-host (bez DJANGO_BPP_HOSTNAME) biorą pierwszą domenę z DJANGO_BPP_HOSTNAMES. Wiele instalacji może dzielić jeden projekt i jeden klucz — każda dostaje własną kontrolę. 4. W panelu Healthchecks ustaw nowej kontroli harmonogram: Cron 45 1 * * *, strefa Europe/Warsaw (ta sama co BPP_CRON_TZ), grace np. 2–3 h (zależnie od rozmiaru bazy i łącza). Domyślny „1 dzień" też działa, ale alarm przyjdzie później. 5. Powiadomienia (Integrations): e-mail, a na telefon np. ntfy — można użyć tego samego serwera i topicu co alerty Netdaty (NTFY_TOPIC).

    Ręczny test: make backup-cycle — w panelu powinny pojawić się start i sukces.

    Własna instancja Healthchecks: DJANGO_BPP_HEALTHCHECKS_URL=https://hc.example.org/ping (domyślnie https://hc-ping.com).

    Co trafia do Healthchecks

    Nazwa hosta (w slugu) i treść pingów: rozmiary archiwów, nazwa katalogu zdalnego, nazwy kroków i końcówka logu cyklu przy błędzie. Żadnych danych z bazy. Ping key nie jest logowany. Pusty klucz = funkcja wyłączona (zero ruchu sieciowego).

    Serwis rclone¶

    rclone jest zadeklarowanym, stale działającym serwisem compose (obraz rclone/rclone, bezczynny sleep infinity), a nie kontenerem docker run --rm odpalanym na czas wysyłki. Powód nie jest estetyczny: compose ściąga obrazy tylko zadeklarowanych serwisów (obraz z docker run byłby pobierany dopiero w nocy), a make up kończy się docker system prune -af, który usuwa obrazy bez skojarzonego kontenera — obraz „gołego" rclone'a znikałby przy każdym deployu.

    W serwisie rclone wykonują się: krok wysyłki i retencji zdalnej cyklu nocnego (przez docker exec z orkiestratora) oraz targety make rclone-config, make rclone-sync i make rclone-check. Katalog $BPP_CONFIGS_DIR/rclone jest tu montowany read-write (rclone dopisuje odświeżone tokeny OAuth do rclone.conf), a katalog backupów — read-only.

    Układ katalogów na zdalnym¶

    Kopie lądują w jednym katalogu na miesiąc:

    backup_enc:
  2026-07/
    db-backup-20260701-023000.tar.gz
    media-backup-20260701-023000.tar.gz
    config-backup-20260701-023000.tar.gz
    ...                                  (3 pliki na dzień)
  2026-08/
    ...
  obrazy/                                (archiwum obrazów — osobno, patrz niżej)
    20261103-014500/
      obrazy.tar.gz
      manifest.txt
      bpp-deploy.bundle

    Wysyłka to rclone copy całego lokalnego katalogu backupów. Ponieważ nazwy niosą timestamp, a katalog docelowy jest stały przez cały miesiąc, copy wysyła tylko to, czego na zdalnym jeszcze nie ma — czyli 2 pliki dziennie. Jednocześnie co noc „pokazuje" zdalnemu całe lokalne okno 7 kopii, więc dzień, w którym rclone padł, uzupełnia się sam następnej nocy.

    Do katalogu miesięcznego wolno wysyłać wyłącznie rclone copy

    rclone sync skasowałby z katalogu miesiąca wszystko, czego nie ma lokalnie — czyli całe archiwum poza ostatnimi 7 dniami — i zakończyłby się sukcesem, bez śladu w logach. Broni tego asercja mutacyjna w make test-rclone.

    Skąd ta zmiana (do sierpnia 2026 było inaczej)

    Wcześniej cykl robił rclone sync /backup/ REMOTE:YYYY-MM/DD/ — do świeżego, pustego katalogu na każdy dzień. Skoro cel był za każdym razem pusty, rclone nie miał czego pominąć i wysyłał całe lokalne okno 7 kopii: 14 plików dziennie zamiast 2, a każdy plik lądował na zdalnym w 7 egzemplarzach. Siedmiokrotny narzut na transferze i na miejscu.

    Katalogi dzienne z tamtego okresu zostają tam, gdzie były — sama wysyłka ich nie rusza. Scalenie do katalogów miesięcznych to jednorazowa, ręczna operacja po stronie backendu (rclone moveto + rclone purge dopiero po weryfikacji, że komplet plików jest już w katalogu miesiąca).

    Ale retencja zdalna owszem je usunie — rclone purge kasuje katalog miesiąca razem z jego podkatalogami DD/. Przy domyślnych 12 miesiącach wszystko starsze zniknie po jednym katalogu na dobę, niezależnie od tego, czy zdążyłeś je scalić. Jeśli zależy Ci na tych danych, scal je zanim retencja do nich dojdzie, albo najpierw ustaw DJANGO_BPP_RCLONE_KEEP_MONTHS=0.

    Retencja zdalna — DJANGO_BPP_RCLONE_KEEP_MONTHS¶

    Domyślnie włączona: 12 miesięcy. Po udanej wysyłce cykl usuwa najstarsze katalogi miesięczne, zostawiając DJANGO_BPP_RCLONE_KEEP_MONTHS najnowszych, licząc z bieżącym.

    Aktywuje się na sam git pull, bez make up

    backup-runner ma katalog ./scripts podmontowany na żywo (./scripts:/scripts:ro), a Ofelia woła /scripts/backup-cycle.sh w działającym kontenerze. Nowy kod wchodzi więc do gry przy najbliższym przebiegu o 01:45 — bez przebudowy, bez restartu, bez make up. Jeśli chcesz najpierw zobaczyć, co by zniknęło: make rclone-check i ustaw DJANGO_BPP_RCLONE_KEEP_MONTHS=0 zanim wykonasz git pull.

    # w $BPP_CONFIGS_DIR/.env
DJANGO_BPP_RCLONE_KEEP_MONTHS=24   # trzymaj 2 lata
DJANGO_BPP_RCLONE_KEEP_MONTHS=0    # wyłącz retencję zdalną całkowicie
DJANGO_BPP_RCLONE_KEEP_MONTHS=     # to samo — pusta wartość też wyłącza

    Każda wartość niebędąca dodatnią liczbą całkowitą (0, puste, śmieci) znaczy wyłączone — nigdy błąd i nigdy kasowanie na chybił trafił.

    Bezpieczniki, każdy celowy:

    • Maksymalnie jeden katalog miesięczny na cykl. W normalnej pracy i tak co miesiąc wypada dokładnie jeden, więc różnicy nie widać — ale instalacja z wieloletnią historią nie traci kilkudziesięciu miesięcy jednej nocy, tylko po jednym na dobę. Każde usunięcie ma osobny wpis w logu i w komunikacie do Rollbara, więc jest doba na reakcję zamiast pojedynczego nieodwracalnego zdarzenia.
    • Bieżący miesiąc nie zostanie usunięty nigdy.
    • Ruszane są wyłącznie katalogi pasujące dokładnie do YYYY-MM. Cokolwiek innego w remote — twoje własne katalogi, stare katalogi dzienne wyniesione na górny poziom, nazwy typu 2026-08-01 czy 99 — jest nietykalne.
    • Błąd retencji nigdy nie wywraca backupu. Nieudany purge czy nieudane listowanie zdalnego to ostrzeżenie w logu i adnotacja w komunikacie sukcesu; kod wyjścia cyklu się nie zmienia. Sprzątanie nie ma prawa zamienić udanego backupu w alert.

    Retencja lokalna (DJANGO_BPP_BACKUP_KEEP_LAST, domyślnie 7 kopii) jest od niej niezależna i działa jak dotąd.

    Archiwum obrazów i repozytorium — praca bez Docker Huba i GitHuba¶

    Backup bazy, mediów i konfiguracji nie wystarcza do postawienia serwera, jeśli akurat Docker Hub albo GitHub nie działa (albo obrazu w danej wersji już tam nie ma). Dlatego nocny cykl trzyma też archiwum obrazów, na których naprawdę działa serwer, oraz git bundle repozytorium bpp-deploy.

    Domyślnie włączone — z rezerwą dysku

    Archiwum zajmuje ok. 1,5 GB lokalnie i tyle samo na zdalnym (dwa zestawy). Żeby nie zapchać dysku, na którym stoi baza, nowy zestaw powstaje tylko wtedy, gdy po jego zapisie zostanie co najmniej 10 GB wolnego i dysk będzie zajęty najwyżej w 80%. Poniżej progu krok jest co noc pomijany z adnotacją obrazy=ZA-MALO-MIEJSCA(wolne 13G, zajete 78%) i sam rusza, gdy przybędzie miejsca — bez zmian w .env. Bez archiwum make restore-server i tak działa: pobiera z Docker Huba obrazy dokładnie w tej wersji, która działała. Zob. wymagania sprzętowe.

    Jeden zestaw to katalog obrazy/<YYYYMMDD-HHMMSS>/ w katalogu backupów:

    Plik Zawartość
    obrazy.tar.gz (.tar.zst, gdy obraz pomocniczy ma zstd) docker save wszystkich obrazów naraz — obrazy iplweb/bpp_* dzielą warstwy, więc w archiwum są raz
    manifest.txt obraz → ID → digest → wersja → usługi, data, wersja i commit bpp-deploy, suma sha256 archiwum
    bpp-deploy.bundle git bundle repozytorium (bieżący commit, gałąź, tagi)

    Które obrazy: dokładnie te, na których chodzą kontenery projektu — ID obrazu brane z kontenera, nie z lokalnego tagu latest (po make pull bez make up tag wskazuje już nowszy obraz niż produkcja). W archiwum są obrazy BPP, postgres (dbserver), owasp/modsecurity-crs (webserver), redis, pgbouncer, ofelia, autoheal, docker:cli orkiestratora, rclone i wszystko inne, co chodzi w projekcie (np. html2docx). Monitoring jest domyślnie pomijany (netdata, loki, grafana, alloy, dozzle, flower — ok. 1 GB, a BPP działa bez niego); dołącza go DJANGO_BPP_BACKUP_IMAGES_MONITORING=1 albo make images-save MONITORING=1.

    Kiedy powstaje: co noc cykl porównuje zestaw obrazów (ref + ID) z manifestem ostatniego zestawu. Nowe archiwum powstaje tylko wtedy, gdy coś się zmieniło — czyli zwykle raz po każdej aktualizacji; w pozostałe noce krok trwa sekundę. Zmiana samego repozytorium (commit bez nowych obrazów) nowego zestawu nie tworzy — wymusza go make images-save FORCE=1.

    Rozmiar: zmierzony dla zestawu bez monitoringu ok. 650–700 MB (gzip -1; tyle samo na klasycznym overlay2 i na store containerd Dockera 29), więcej przy dołączonym monitoringu. Przed zapisem cykl sprawdza wolne miejsce: liczy unikalne warstwy wszystkich obrazów (rozmiar przed kompresją, każda wspólna warstwa raz, tak jak trafia do archiwum) plus 10% zapasu — czyli nadal z górką. Wcześniej sumował rozmiary obrazów, a pięć obrazów BPP dzielących niemal wszystkie warstwy liczył pięć razy (szacunek ~8,6 GiB przy realnych ~4,7 GiB), przez co rezerwa niepotrzebnie pomijała archiwum. Gdy warstw obrazu nie da się sparować z docker history, ten obraz wchodzi do szacunku w całości. Przy braku miejsca krok jest pomijany z adnotacją obrazy=BRAK-MIEJSCA.

    Na zdalnym zestawy leżą w osobnym katalogu REMOTE:obrazy/, nie w katalogu miesięcznym:

    • katalog miesięczny dostaje co noc całe lokalne okno kopii — zestawy obrazów lądowałyby w każdym nowym miesiącu od nowa (1,5–3 GB duplikatu miesięcznie);
    • retencja miesięczna skasowałaby jedyny zestaw, gdyby obrazy nie zmieniały się dłużej niż DJANGO_BPP_RCLONE_KEEP_MONTHS.

    Wysyłka to tak samo wyłącznie rclone copy (nigdy sync — pusty lokalny katalog na świeżym serwerze skasowałby ze zdalnego archiwum potrzebne do odtworzenia). Zdalnie zostaje DJANGO_BPP_BACKUP_IMAGES_KEEP_LAST najnowszych zestawów; nadmiar jest usuwany po jednym na cykl i tylko po udanej wysyłce.

    Zmienne w $BPP_CONFIGS_DIR/.env (czytane co noc z pliku — zmiana działa bez make up; żadna nie jest wymagana):

    DJANGO_BPP_BACKUP_IMAGES_ENABLED=0      # wyłącz archiwum obrazów (domyślnie włączone)
DJANGO_BPP_BACKUP_IMAGES_KEEP_LAST=3    # ile zestawów lokalnie i zdalnie (domyślnie 2)
DJANGO_BPP_BACKUP_IMAGES_MONITORING=1   # dołącz monitoring
DJANGO_BPP_BACKUP_IMAGES_MIN_FREE_GB=15 # rezerwa: tyle GB ma zostać wolne (domyślnie 10, 0 = bez)
DJANGO_BPP_BACKUP_IMAGES_MAX_USED_PCT=85 # rezerwa: najwyżej tyle % zajęte (domyślnie 80, 0 = bez)

    Limit miejsca na zdalnym

    Dwa zestawy to ok. 1,5 GB dodatkowego miejsca na zdalnym (więcej z monitoringiem). Rezerwa pilnuje tylko dysku lokalnego — jeśli udział zdalny ma twardy limit, policz go albo ustaw DJANGO_BPP_BACKUP_IMAGES_ENABLED=0. Archiwum nie zawiera sekretów (publiczne obrazy i publiczne repozytorium), ale i tak jedzie przez ten sam (szyfrowany) remote co reszta kopii.

    Błąd tego kroku — docker save, brak miejsca, nieudana wysyłka — nigdy nie zmienia wyniku cyklu: to adnotacja obrazy=... w komunikacie (nowe(650.2MiB), bez-zmian, wylaczone, ZA-MALO-MIEJSCA(...), BRAK-MIEJSCA, BLAD(exit=N), BRAK-MOUNTU(make up), wysylka=BLAD). Krok wymaga mountu repozytorium w backup-runner (.:/repo:ro), więc po git pull potrzebny jest make up — do tego czasu adnotacja BRAK-MOUNTU(make up) i backup bazy idzie normalnie.

    Ręcznie — make images-save¶

    make images-save              # nowy zestaw tylko, gdy obrazy się zmieniły
make images-save FORCE=1      # wymuś nowy zestaw (np. po commicie bez nowych obrazów)
make images-save MONITORING=1 # z monitoringiem

    Działa w kontenerze backup-runner — ten sam kod co krok nocny. Wymaga działającego stacka (archiwizuje obrazy działających kontenerów); bez appserver albo dbserver odmawia (exit 5).

    Wczytanie — make images-load¶

    make images-load FILE=~/backups/obrazy/20261103-014500

    Działa na świeżym hoście bez .env (jak restore-config). Kolejno: sprawdza sumę sha256 archiwum z manifestem (uszkodzone pobranie nie trafia do Dockera), docker load, potem dla każdego obrazu z manifestu weryfikuje zgodność — po ID albo, gdy nowy host ma inny magazyn obrazów (klasyczny overlay2 kontra containerd liczą ID inaczej), po odcisku warstw. Na końcu przypina nazwy z compose (np. iplweb/bpp_appserver:latest) do wczytanych obrazów i dodaje tag wersji CalVer obrazom BPP. Po tym make up (nie make run — ten zaczyna od docker pull) startuje wszystko z lokalnych obrazów.

    Repozytorium bez GitHuba:

    git clone ~/backups/obrazy/20261103-014500/bpp-deploy.bundle ~/bpp-deploy

    Skąd wziąć pliki na nowym serwerze, gdy Docker Hub nie działa: obraz rclone/rclone też jest na Docker Hubie, więc do pobrania kopii użyj rclone zainstalowanego na hoście (pakiet dystrybucji albo binarka z rclone.org) i tego samego rclone.conf (hasło remote'a crypt musisz znać):

    rclone copy backup_enc:obrazy/20261103-014500/ ~/backups/obrazy/20261103-014500/

    Konfiguracja zdalnego — make rclone-config¶

    make rclone-config uruchamia interaktywny kreator rclone config wewnątrz serwisu rclone. Powstały plik ląduje w $BPP_CONFIGS_DIR/rclone/rclone.conf (bind mount, więc przeżywa odtworzenie kontenera) i to jego czytają make rclone-sync, make rclone-check i nocny cykl.

    Nazwa remote'a musi się zgadzać z DJANGO_BPP_RCLONE_REMOTE w .env (domyślnie backup_enc:).

    read-only file system przy zapisie konfiguracji

    Symptom — kreator na każdą odpowiedź odpowiada:

    ERROR : Failed to save config after 10 tries: failed to create temp file
for new config: open /config/rclone/rclone.conf1427152738:
read-only file system

    i mimo to brnie dalej, więc można przeklikać całą konfigurację i dopiero na końcu odkryć, że nic nie powstało.

    Przyczyna. Do września 2026 katalog rclone był montowany :ro (od pierwszego commita — czyli make rclone-config nie zadziałał ani razu). rclone tego pliku nie tylko czyta: zapisuje go przez plik tymczasowy + rename w tym samym katalogu. Wymaga tego również normalna praca z remote'em OAuth — dokumentacja rclone, opcja --config:

    When token-based authentication are used, the configuration file must be writable, because rclone needs to update the tokens inside it.

    Dla większości remote'ów (Dropbox, Google Drive) :ro oznacza tylko hałas w logu — refresh-token się nie zmienia, więc kolejne odświeżenie i tak się uda. Ale tam, gdzie refresh-token jest jednorazowy, brak zapisu rozwala autoryzację na trwałe: dokumentacja Boxa w rclone cytuje „Each refresh_token is valid for one use in 60 days" i ostrzega, że po nieudanym odświeżeniu dostaniesz Invalid refresh token i trzeba przejść OAuth od nowa.

    Rozwiązanie — git pull && make up. Sam git pull nie wystarczy: zmiana siedzi w volumes: w docker-compose.backup.yml, więc kontenery muszą się odtworzyć. Po make up kreator działa w serwisie rclone, który montuje katalog konfiguracyjny read-write — obejścia nie są już potrzebne.

    Właściciel pliku — poprawiany automatycznie

    Kreator działa jako root w kontenerze, więc rclone.conf powstałby na hoście jako root:root. Backupom to nie przeszkadza (kontener też jest rootem), ale przy przenosinach serwera rsync uruchomiony z konta operatora takiego pliku nie przeczyta — i nowy serwer wstałby bez konfiguracji backupu zdalnego.

    Dlatego make rclone-config po zamknięciu kreatora wyrównuje właściciela pliku do właściciela katalogu $BPP_CONFIGS_DIR/rclone/ i zwęża prawa do 0600 (funkcja rclone_fix_config_owner w scripts/lib-rclone.sh). Gdyby się nie udało, zobaczysz UWAGA: z kodem błędu — backupy działają dalej, ale katalog konfiguracyjny przenoś wtedy przez sudo rsync.

    Backup konfiguracji (.env)¶

    Zrzut bazy bez katalogu konfiguracyjnego jest tylko w połowie użyteczny. $BPP_CONFIGS_DIR/.env trzyma m.in. hasło bazy, DJANGO_BPP_SECRET_KEY i klucz szyfrowania sekretów integracji DJANGO_BPP_FIELD_ENCRYPTION_KEY (patrz Architektura konfiguracji). Bez tego klucza tokeny PBN, hasło Clarivate, sekret ORCID i hasło DSpace w odtworzonej bazie są nieczytelne. Dlatego katalog konfiguracyjny jest archiwizowany tak samo jak baza:

    • ten sam cykl — nocny backup-cycle (01:45) robi config-backup-<TS>.tar.gz zaraz po zrzucie bazy i mediów, z tym samym timestampem;
    • to samo miejsce — osobny plik obok zrzutów w $DJANGO_BPP_HOST_BACKUP_DIR (nie wewnątrz dumpu bazy);
    • ta sama rotacja — DJANGO_BPP_BACKUP_KEEP_LAST (domyślnie 7) i ta sama wysyłka na zdalny (rclone copy całego katalogu backupów, katalog miesięczny);
    • tryb 0600, właściciel = właściciel katalogu backupów (żeby make restore-config działał z konta operatora bez sudo).

    Archiwum obejmuje cały $BPP_CONFIGS_DIR: .env, rclone/rclone.conf (z hasłem remote'a backup_enc:), ssl/, letsencrypt/, konfigurację monitoringu. Pominięte są logi (logs/, *.log). To kilka–kilkadziesiąt KiB.

    Kto ma backup, ma dane i klucz

    Backup konfiguracji zawiera klucz szyfrowania sekretów, więc katalog backupów (i zdalny remote) trzeba chronić tak jak sam serwer — kto ma backup, ma też dane i klucz.

    Wymaga make up po aktualizacji

    Orkiestrator potrzebuje nowego mountu ${BPP_CONFIGS_DIR}:/configs:ro w docker-compose.backup.yml, a mounty wchodzą dopiero przy make up. Do tego czasu cykl nocny działa jak dotąd (baza + media), loguje UWAGA: brak /configs/.env ... i dopisuje config=BRAK-MOUNTU(make up) do komunikatu w Rollbarze. Błąd archiwizacji konfiguracji nigdy nie wywraca backupu bazy (kod wyjścia cyklu się nie zmienia) — jest ostrzeżeniem w logu i adnotacją config=BLAD(...) w komunikacie.

    Hasło do kopii zdalnej — w menedżerze haseł

    Kopia zdalna jest szyfrowana przez remote backup_enc: (rclone crypt), którego hasło siedzi w rclone.conf — czyli w tym samym katalogu, który archiwizujemy. Po utracie serwera zdalnej kopii nie da się odszyfrować bez tego hasła: zapisz hasło (i salt) backup_enc: w menedżerze haseł.

    Ręczny backup — make config-backup¶

    make config-backup    # samo archiwum konfiguracji
make backup           # baza + media + konfiguracja, jeden timestamp

    Działa w efemerycznym kontenerze na obrazie backup-runnera (jak media-backup), więc nie wymaga działającego stacku i czyta także pliki root:root (np. letsencrypt/).

    Odtworzenie — make restore-config¶

    make restore-config FILE=~/backups/config-backup-20261024-023000.tar.gz
make restore-config FILE=... ONLY_ENV=1     # tylko .env, reszta katalogu nietknięta

    Co robi scripts/restore-config.sh:

    1. Sprawdza archiwum (odmawia wpisów absolutnych i z ..) i rozpakowuje je najpierw do prywatnego katalogu tymczasowego.
    2. Gdy docelowy .env istnieje — pokazuje różnice (tylko nazwy zmiennych, bez wartości; osobne ostrzeżenie, gdy zmienia się DJANGO_BPP_FIELD_ENCRYPTION_KEY) i pyta o potwierdzenie. Trzeba wpisać tak; cokolwiek innego, EOF albo brak terminala = nic nie zostaje zmienione. (Bez pytania: BPP_RESTORE_CONFIG_YES=1.)
    3. Przed nadpisaniem zapisuje kopię: .env.przed-restore-<TS> (0600) obok .env, a przy pełnym restore także archiwum dotychczasowego katalogu config-przed-restore-<nazwa>-<TS>.tar.gz (0600) w katalogu nadrzędnym.
    4. Rozpakowuje archiwum z zachowaniem uprawnień i ustawia .env na 0600.

    Po odtworzeniu: make up (albo make restore + make up, jeśli odtwarzasz też bazę). Klucz z .env musi pochodzić z tego samego okresu co baza — .env sprzed dodania klucza nie odczyta sekretów zaszyfrowanych później.

    Nowy serwer po awarii¶

    Kopie są tylko na zdalnym?

    Całość — wybór kompletu, pobranie, konfiguracja, obrazy, baza, media, make up — robi make restore-server: patrz Odtworzenie serwera po awarii. Poniżej wariant ręczny, z backupów leżących już na dysku.

    Na świeżym hoście nie ma repo-lokalnego .env, więc make uruchomiłby setup → init-configs, który wygenerowałby nowe sekrety, w tym nowy klucz szyfrowania. Zamiast tego:

    git clone https://github.com/iplweb/bpp-deploy.git ~/bpp-deploy && cd ~/bpp-deploy
# skopiuj backupy (z dysku albo: rclone copy backup_enc:YYYY-MM/ ~/backups/)
make restore-config FILE=~/backups/config-backup-<TS>.tar.gz \
    BPP_CONFIGS_DIR=/home/bpp/moja-instancja
make restore          # baza + media z tego samego <TS>
make up

    restore-config działa bez repo-lokalnego .env i sam go zapisuje (BPP_CONFIGS_DIR + COMPOSE_PROJECT_NAME = nazwa katalogu, ta sama reguła co init-configs). Przy bazie zewnętrznej dopisz tam ręcznie BPP_DATABASE_COMPOSE=docker-compose.database.external.yml.

    Awaria TLS: certificate signed by unknown authority¶

    Symptom — rclone nie dogaduje się ze zdalnym, a komunikat sugeruje wygasły token:

    ERROR : : error listing: Post "https://api.dropboxapi.com/2/files/list_folder":
couldn't fetch token - maybe it has expired? - refresh with "rclone config reconnect backup:":
Post "https://api.dropboxapi.com/1/oauth2/token":
tls: failed to verify certificate: x509: certificate signed by unknown authority

    Pierwsza połowa komunikatu myli. Token jest w porządku — kontener nie ma magazynu certyfikatów CA, więc padnie każde połączenie HTTPS, nie tylko do Dropboksa.

    Historia. Do września 2026 backup-runner stał na obrazie postgres (Debian), który purge'uje ca-certificates na końcu builda, i doinstalowywał rclone w runtime bez żadnego roota CA — stąd ta awaria. Była niema: notyfikacja Rollbara szła tym samym zepsutym HTTPS-em, więc alert o exit 3 (rclone copy failed) dostawał http=000 i nigdy nie docierał; lokalne kopie powstawały normalnie, brakowało wyłącznie wysyłki. Pierwotna przyczyna zniknęła razem z apt-get: dziś rclone działa w dedykowanym serwisie rclone na obrazie rclone/rclone, który bundle CA ma wbudowany.

    Dlaczego sonda CA mimo to została. Healthcheck serwisu rclone nadal sprawdza niepusty /etc/ssl/certs/ca-certificates.crt: BPP_RCLONE_IMAGE pozwala podstawić dowolny obraz, a brak CA nie objawia się niczym aż do nocnego cyklu — sonda robi z niekompatybilnego obrazu kontener unhealthy już przy make up. Nie usuwaj jej.

    Diagnoza (gdyby symptom wrócił, np. po podmianie BPP_RCLONE_IMAGE):

    docker compose ps rclone
# unhealthy -> healthcheck wykrył brak CA albo niedziałające `rclone version`
docker compose exec rclone ls -l /etc/ssl/certs/ca-certificates.crt
# brak pliku -> to ta usterka
docker compose logs ofelia | grep -i backup_cycle | tail -20
# "rclone-copy (exit=3)" wskazuje, od kiedy wysyłka nie działa

    Rozwiązanie — wróć na domyślny obraz (usuń BPP_RCLONE_IMAGE z .env) albo wskaż obraz z bundlem CA, po czym make up.

    Po naprawie zaległe kopie uzupełnią się same przy najbliższym cyklu: na zdalny wysyłany jest cały $DJANGO_BPP_HOST_BACKUP_DIR, a nie tylko dzisiejsze pliki.

    make backup / make restore — para baza + media¶

    make backup uruchamia db-backup (równoległy pg_dump -Fd, tar.gz) i media-backup (zawartość wolumenu media jako tar.gz). Oba archiwa lądują w $DJANGO_BPP_HOST_BACKUP_DIR z timestampem:

    • db-backup-YYYYMMDD-HHMMSS.tar.gz
    • media-backup-YYYYMMDD-HHMMSS.tar.gz

    make restore automatycznie wybiera najświeższą parę (lub --pick / --timestamp=...). Przed destruktywnym restorem robi safety-backup aktualnej bazy — procedura jest odwracalna. Wykorzystywane przy przenosinach serwera.

    Co NIE jest backupowane przez make backup¶

    make backup zapisuje bazę danych, wolumen mediów i katalog konfiguracyjny. Loki/Netdata/Grafana (logi i metryki historyczne) nie są przenoszone — po starcie na nowym hoście zaczynają od pustego stanu. Jeśli zależy Ci na historii monitoringu, skopiuj dodatkowo wolumeny loki_data, netdata_lib, netdata_cache i grafana_data (przy zatrzymanym stacku):

    docker run --rm -v <vol>:/data alpine tar czf - /data | ssh nowy-host 'cat > vol.tar.gz'
